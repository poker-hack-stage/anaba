### 画面-2: 候補カードに所要時間・選ばれた理由・時刻を載せるか（状態: 承認待ち）

**推奨: 所要時間と選ばれた理由は載せる。時刻は載せない。**

| 項目           | 推奨     | #18 のレスポンス（`PlanCandidate`）に足すもの                                           | 出し方                                                                                                                 |
| -------------- | -------- | --------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------- |
| 選ばれた理由   | 載せる   | `reason: string`（1〜2文。選んだ条件のどれにどう合うか）                                | Claude が書く。デモモード（#19）は「興味の『温泉』に合うスポットを評価の高い順に選びました」のような定型文             |
| 所要時間の目安 | 載せる   | `durationMinutes: number`（候補全体）。経路の各スポットには今ある `stay_minutes` を使う | サーバー側で計算する: 各スポットの `stay_minutes` の合計＋移動の目安 ×（スポット数−1）。移動の目安は移動手段ごとの定数 |
| 時刻           | 載せない | なし                                                                                    | —                                                                                                                      |

理由:

- 候補を並べて比べるのがこの画面の役目（参考 PoC はプランを1件だけ出していた）。比べるときに効くのは「なぜこの候補か」と「どれくらいかかるか」
- 所要時間を Claude に書かせると、スポットのデータと合わない数字が出ても確かめられない。`stay_minutes` と定数から計算すれば、デモモードでも同じ値になり、テスト（#24）も書ける
- 時刻（「9:00 わさび田」のような表）は、営業時間のデータがなく（`best_time` は自由文）、正しいか確かめられない。日帰りだけにする（データ-4）ので、順番と所要時間があれば足りる

移動の目安の定数（案。#18 で決める）: 車 20分・電車・バス 40分・自転車 30分（本数の少ない路線バスや坂道を考えて、車より長めに取る）。

あわせて決めること（#18 の「スポットのデータにない立ち寄り先」）: **推奨は入れない。** 地図にピンを立てられず、詳細（#22）も開けないため。入れる場合は、経路とは別の `tips: string[]`（「地元の食堂でランチ」のような一言）としてカードの下に文字だけで出す。

代替案:

- 時刻も載せる（参考 PoC と同じ。Claude に開始時刻と各スポットの到着時刻を書かせる。見栄えはよいが、正しさを確かめられない）
- 所要時間も Claude に書かせる（サーバーの計算が要らない。数字の根拠が説明できない）

推奨 A の決めごと:

- スポットの件数（#30 の「1地域6件以上」）はそのままでよい。重なりが気になれば、見せる地域だけ8件に増やす

### データ-4: 1泊2日・2泊3日を残すか（状態: 承認待ち）

**推奨: 残さない。日帰りだけにし、フォームから日程の項目を外す。** ページの見出しを「日帰りの旅の候補を提案します」のように書き、日帰りが前提だとわかるようにする。`PlanConditions` の `duration` はなくす（#17）。`days[]` は作らない（#18）。

理由:

- 1地域のスポットは6件前後（#30）で、経路は最大4件（`MAX_ROUTE_LENGTH`）。2泊3日を1地域で組むと、スポットが足りない
- 複数日にすると、宿の扱い・日ごとの `days[]`・デモモードの組み立て（#19）・カードの表示（#20）がそれぞれ重くなる
- 今のコードでは、日程はタイトルの文言（「〜をめぐる1泊2日プラン」）に入るだけで、中身は変わっていない

代替案:

- 「半日／日帰り」の2択に置き換える（半日＝経路2〜3件、日帰り＝4件。データの量で作れて、選ぶ楽しさは残る）
- 今の3択を残し、#18 の候補を日ごとの `days[]` で表す（参考 PoC と同じ。スポットを1地域10件以上に増やすか、複数日の候補は複数の地域にまたがってよいことにする必要がある）

## 5. 技術の細部

### 技術-1: Claude の既定モデル（状態: 承認待ち）

**推奨: `claude-sonnet-5`。** `ANTHROPIC_MODEL` を指定すれば `claude-opus-5-5` に切り替えられる（#7）。

理由:

- 頼む仕事は、30件前後のスポットから条件に合うものを選んで並べ、決まった形の JSON で返すこと。深い推論より、応答の速さ（#18 の `maxDuration` の中に収め、デモで待たせない）と料金を優先したい
- Claude API は従量課金で無料枠がない。料金の差は Anthropic の料金ページで #7 の担当者が確かめる

代替案:

- `claude-opus-5-5`（候補の質・説明文の質を優先。応答は遅く、料金は高くなる）
- 既定は `claude-sonnet-5` のまま、発表当日だけ `ANTHROPIC_MODEL=claude-opus-5-5` にする

確かめられていないこと: 実際の応答時間と1回あたりの料金は測っていない（API キーがないため）。#7 で両方のモデルを一度ずつ呼んで比べ、推奨を直す余地を残す。
